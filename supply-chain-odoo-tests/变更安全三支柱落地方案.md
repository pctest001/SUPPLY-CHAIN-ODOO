# 变更安全三支柱落地方案（主方案 v2）

> 取代思路：v1《需求知识库落地方案》试图重建完整历史需求（考古范式），成本高、概率性、见效慢。  
> v2 范式转换：QA 需要历史需求的真实目的是「新变更不破坏老行为」，  
> 而这不需要先知道历史需求是什么——用行为差分直接保护全部现状（含从未归档的口头共识）。  
> 原 v1 文档降级为支柱二的工具箱参考，机制全部保留、按需调用。



---

## 一、目标与三支柱总览

| 支柱     | 解决什么                 | 生效时间    |
| ------ | -------------------- | ------- |
| 一：行为围栏 | 保护全部历史行为不被无意破坏（含暗需求） | 场景库跑通当天 |
| 二：按需考古 | 变更半径内的需求条目化（理解「为什么」） | 每次迭代按需  |
| 三：增量止血 | 新需求出生即条目化，债务停止增长     | 门禁上线当天  |

核心关系：**围栏管安全，考古管理解，止血管未来。知识库不再是前置工程，而是二、三支柱运行中的副产品。**

## 二、支柱一：行为围栏（核心）

### 2.1 原理

同一批业务场景在**基线版本**与**变更版本**上各跑一遍，采集全部可观测输出并做差分。  
**差异 − 本次意图清单 = 回归嫌疑**。人只裁决「这个差异是不是本次故意改的」（对照新 PRD，秒判），不再裁决「历史需求是什么」（无据可判）。

### 2.2 组件设计（复用现有设施）

```
fence/
├── scenarios/            # 场景库：JSON 声明式场景（输入序列 + 观测点）
│   └── s001_po_flow.json
├── runner.py             # 双版本执行器：对 base/head 各跑一遍场景
├── capture.py            # 输出采集：API 响应 / DB 状态快照 / 报表数字
├── normalize.py          # 归一化：时间戳、自增ID、UUID、序列号 → 占位符
├── diff.py               # 差分引擎：逐场景逐观测点比对 → diff_report.json
├── intents.yml           # 本次意图清单：声明「预期会变」的观测点（关联 REQ id）
└── verdict.py            # 差异 − 意图 = 回归嫌疑清单；全绿/嫌疑 N 条
```

- **双版本环境**：复用 `docker-compose.test.yml`，起两套实例（base=main 最新 tag，head=当前分支），不同端口。
- **场景库来源**（先低成本铺量）：① 现有 56 条测试用例的输入序列直接转化；② `prod_fixtures.json` / `seed_live.py` 的种子数据组合业务流；③ 后续按模块补手工场景。
- **观测点三类**：API 响应体（去动态字段）、关键表状态快照（订单/库存/审批记录，白名单表）、报表输出数字。
- **归一化规则**（假差异清零是围栏可用性的生死线）：时间戳 → `<TS>`；自增 id/序列号 → 按首次出现顺序重编号；UUID → `<UUID-n>`；浮点 → 保留 2 位。

### 2.3 意图清单（intents.yml 格式）

```yaml
iteration: "2026-S15 采购审批简化"
intents:
  - req: REQ-PO-021
    desc: 10万以下免审批
    expect_changes:
      - scenario: s001_po_flow
        observe: po.state after submit
        from: pending_approval
        to: approved
```

裁决规则：差异命中 intents → 预期变更 ✓；未命中 → 回归嫌疑，出现在报告里必须逐条处理（确认放行=补 intents，确认回归=打回修复）。**嫌疑清单不清零不许合入。**

### 2.4 CI 集成

新增 `behavior-fence` job：起双环境 → 跑场景库 → diff → verdict。产出 `fence/diff_report.json`，接入 `reports/` 仪表盘新卡片「行为围栏」（场景数/差异数/嫌疑数/放行数）。

### 2.5 已知代价（明示，不回避）

1. 围栏保护的是现状，**现状里的 bug 也被保护**——防退化不辨对错，辨对错走支柱二。
2. 保护范围 = 场景库覆盖面，没被踩到的行为不设防 → 场景库覆盖率是核心运营指标，进仪表盘。
3. 归一化是持续维护的脏活，新的动态字段会不断出现 → normalize 规则表开放可配。

## 三、支柱二：按需考古（工具箱，不做批量工程）

**触发时机**（仅两种，其余时间不动）：

1. 围栏报警后需要判断「这个被撞到的行为到底是需求还是 bug」；
2. 本次迭代要动模块 X，PM/QA 需要理解 X 的存量规则。

**动作**：只对变更半径（本次 diff 涉及的文件/模块）执行工具箱中的手段，产出薄条目入 KB。

**工具箱清单**（详细机制见 v1 文档《需求知识库落地方案.md》，此处仅索引）：

- 四源交叉验证 + 证据签名（代码/测试/PRD/技术方案，缺源即诊断）
- 岁月验证四象限（git 年龄 × 调用热度；热度数据缺失时降级二维，confidence 上限 0.75）
- 数据考古（SQL：状态值分布/事实必填/时间戳顺序/数据断层）
- 视图逆向（Odoo view XML 的必填/只读/可见性条件，解析成本最低，优先用）
- bug 单考古 / 多模型抽取投票（可选）

**明确不做**：全量条目化、全量四源匹配、全量文档回填。冷代码永远不考古。

## 四、支柱三：增量止血

### 4.1 KB 薄存储（保留 v1 Phase 0，缩水版）

```
kb/
├── model.py     # Requirement dataclass + provenance/status 枚举（沿用 v1 schema）
└── store.py     # JSONL 读写 + 按模块/状态过滤
data/requirements.jsonl
```

只存两类条目：① 新迭代的需求（出生即条目化）；② 支柱二按需考古的产出。不存全量历史。

### 4.2 门禁

- **合入门禁**：PR 描述必须含 `REQ-xxx` 关联（CI 正则检查），无关联不合入；
- **意图门禁**：intents.yml 中每条 intent 必须挂 REQ id——想改行为，先把需求写成条目；
- **口头共识截流**：线下达成一致 → 当场 5 分钟录一条 REQ（provenance=oral），谁拍板谁录。

## 六、风险与回退

| 风险                        | 缓解                                          |
| ------------------------- | ------------------------------------------- |
| 假差异淹没真嫌疑（归一化不全）           | P1 验收标准就是「同版本自比对零差异」，不达标不进 P2               |
| 场景库覆盖不足给人虚假安全感            | 覆盖率进仪表盘常驻；每次线上 badcase 复盘第一问：围栏为什么没拦住 → 补场景 |
| 双环境资源/时间成本                | 场景分级：冒烟集每次 PR 跑，全量集每日跑                      |
| 意图清单被滥用（差异一律补 intents 放行） | 放行必须挂 REQ id + 报告留痕，放行数进卡片可审计               |

**回退**：三支柱全部是新增文件与新增 CI job，不改现有 L1–L6 任何模块；任一支柱停用即回到现状，零破坏。

## 八、落地实录（P0–P4 完成，2026-07-27）

全部五阶段已落地并逐项通过验收。以下记录**实际实现与本方案设计稿的偏差**——以代码为准，本节即差异清单：

### 8.1 实际文件布局（与 2.2 设计稿的差异）

```
fence/
├── context.py     # 【新增】Target 连接描述 + build_context 符号上下文（设计稿没有）
├── engine.py      # 声明式场景引擎，raw capture（设计稿的 capture.py 并入此处，无独立文件）
├── runner.py      # CLI：--target head|base --run-id（base/head 必须同 run-id 对齐 $uniq）
├── scenarios/     # 23 个场景（po_approval 9 + receipt_lot 7 + purchase_request 7）
├── normalize.py   # 语义位置归一化（见 8.2，与设计稿规则不同）
├── diff.py        # 归一化后差分 → captures/diff_report.json（有差异 exit 1）
├── intents.yml    # 见 8.3，格式与 2.3 设计稿不同
└── verdict.py     # diff − intents → captures/verdict_report.json（suspects>0 = BLOCK）

kb/
├── model.py           # Requirement dataclass；oral 缺 notes 校验必失败
├── store.py           # 【偏差】存储为单 JSON kb/requirements.json，非 JSONL——
│                      #  单文件让 KB 变更完整出现在 PR diff 里，更利评审
├── gate.py            # PR 文本/intents 的 REQ 引用门禁
├── reverse_views.py   # 支柱二工具箱首件：视图 XML 逆向 → candidates_views.json
└── requirements.json  # 已播种 23 条（provenance=current-prd，挂场景链接）
```

### 8.2 归一化规则（P1 血泪教训，推翻设计稿 2.2 的写法）

设计稿「自增 id 按首次出现顺序重编号」在前哨对比中产生假差异（base 新库 id=12 逃过数值阈值）。
最终规则：**只按已知语义位置清洗，严禁用数值特征猜 id**——删 dict `id` 键、
m2o `[id,名称]→名称`、domain id 三元组→`«IDS:n»`、单号→`«PO»`/`«IN»`、
绝对日期→相对天数 `«D+180»`、run_id→`«RUN»`。此规则写入 normalize.py docstring 作红线。

### 8.3 intents.yml 实际格式

```yaml
version: 1
intents: []        # 每条：req + reason + scenarios（必填）+ paths（可选 glob）
```

与设计稿 2.3 的差异：不写 from/to 期望值（维护成本高且脆），只声明「哪些场景的哪些
观测路径预期会变」；verdict 額外报 **stale intent**（声明了变更但没观测到）防意图腐化；
**合并后必须清空回 `[]`**，防止积累成万能放行。

### 8.5 遗留与注意

- `behavior-fence` job 尚未在真实 GitHub PR 上跑过，首次可能需磨合 1–2 处（base DB 每次从零初始化，预计 6–10 分钟）。
- 门禁只查 PR 标题+描述，不查逐条 commit——squash 合并策略下才最严。
- 视图逆向发现的 E1（供应商协同）/ai.chat 未覆盖按钮：待补场景或人工确认后用
  `python -m kb.store add` 登记（provenance=code-inferred，confidence 0.6）。
