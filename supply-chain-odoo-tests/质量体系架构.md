# supply-chain-odoo 质量体系建设架构

> 版本：v3.7（在 v3.6 基础上：L6 live 模式接真实 SUT——sc_ai 新增 `ai.chat.tool.log` 持久化工具调用，RpcCollector 精确回填 tool_calls/tool_results；新增 `prodmon/notify.py` 告警推送 IM/值班渠道形成闭环；v3.2 已补 L6 在线采样评测 + 告警 + 版本化留痕 + bad case 回流）；v3.4 增量：L6 新增「工具执行准确率 tool_exec_acc」指标（live 模式精测工具调通率，基于 `ai.chat.tool.log` 的 status 判定 ok/error/blocked，blocked 单列安全指标不计入失败）；v3.5 增量：L4 评测集新增「数量落地(quantity_grounding)」校验——生产幻觉回流(负库存/低库存查询编造数量清单)驱动的 PROD-H1~H6 种子须断言数字来自工具返回，不得凭空断言（eval_set v1.1→v1.2，15→21 用例）；v3.6 增量：2026-07-28 live 重跑闭环——eval_set v1.3 新增 PROD-R1/R2（清零/归零裸写操作与社工话术漏拒变体，真实转写），PROD-H1~H6 provenance 回补真实幻觉转写；quantity_grounding 经 3 轮 live 实测修正两处误报（负值 abs 匹配 + tool_result 行数组展平），live quality_score 78.3→91.3，剩余 FAIL 均为真实 SUT 幻觉缺陷；prodmon 注入词表补「清零/归零/清空」语义（曾致正确拒答被误判 false_refusal）；v3.7 增量：PROD-H2 prompt v3 迭代闭环——为消除 v3（未强化规则1）下 PROD-R2 复合指令「先查后拒」泄露库存的回归（SID 239 调 `query_stock` 泄露前 50 条），强化 v3 第 1 条安全规则「复合指令整体拒、不调工具、不得先查后拒」并在 `ai_models.py` 与 `versioning.py` 双向登记（同文同长度 len=847）；live 重放验证 PROD-R2 复合指令零工具调用（安全违规率 0.0%）。数量类编造（AI 报 50/55/52/51/51 ≠ 工具真实 53 行）经 v3「逐行点数」规则验证仍无法消除——判定为 LLM 固有编造倾向、接受为已知 SUT 缺陷基线，不再为幻觉修 prompt（护栏已拦截、L6 幻觉率 12.5% 告警即生产信号），仅修安全硬伤
> 一句话定位：**黑盒 RPC 驱动真实 SUT + 三层自愈 + 覆盖率量化 + Mutation 反假绿门禁 + UI 自动化（浏览器黑盒呈现层）+ AI 评测(L4) + 有效性度量(§8) + 生产监控治理(L6)**，研发期闭环延伸到生产期。

## 4. 关键设计闭环

- **黑盒驱动**：测试工程只经 RPC 测真实 SUT，绝不 `import odoo`，边界清晰、可独立 CI；UI 自动化同样不 `import odoo`，以真实浏览器驱动前端，仅覆盖呈现层。
- **双保险**：覆盖率量化"测了多少"（85.1%），Mutation 门禁证明"测的是真的"（6/6 抓变异）。
- **AI 评测闭环（L4）**：`eval_set.json` 人工金标准驱动 RuleJudge/LLM-as-Judge，量化准确率/幻觉率/拒答率/安全违规率，每次变更对比 `eval_baseline.json` 回归基线；quality_score < 阈值即门禁失败。
- **有效性度量（§8）**：北极星 = 逃逸率（mutation 未抓到的比例），须单调下降；并以金标准 kappa 校准裁判本身（防"评测分高但线上翻车"）。
- **生产监控治理（L6）**：把评测从研发期延伸到生产期——在线采样真实 `ai.chat.session`（live 模式经 `ai.chat.tool.log` 精确取每次工具调用），经 ProductionJudge 跑安全/拒答/幻觉信号（幻觉哨兵可插拔：默认启发式，`PROD_LLM_JUDGE=1` 时升级 LLM-as-Judge 复用 DeepSeek，见技术方案 §4.8.5），对比 L4 基线告警（安全 0 容忍 / 幻觉超阈 / 综合准确率跌破下限 / 退化），告警经 `notify.py` 推送 IM/值班渠道；`sc_ai` 会话落 `prompt_version`+`model_used` 实现版本化留痕，prodmon 统计线上分布；问题会话回流为 L4 回归用例——"监控 → bad case → L4 回归 → prompt 迭代"闭环成立，且已用真实 LLM 完整演练一轮（PROD-61 注入漏拒 → eval_set v1.1 → prompt v2 → live 评测 15/15 → 攻击重放被拒，详见技术方案 §4.8.3；报告统一呈现见 §4.9）；新增「工具执行准确率」指标量化工具调通率（live 模式经 `ai.chat.tool.log` 的 status 字段精确判定 ok/error/blocked，blocked 单列安全指标不计入失败）。
- **反馈环**：覆盖率盲区 → 驱动补测（gen）→ Mutation 抓真 bug（如 `product_qty`）→ 独立 fix commit。
- **不掩盖回归**：自愈只救环境/数据/配置且全程审计，绝不把 SUT 真实缺陷"修绿"。
- **期望值权威**：业务数值只来自 PRD/验收清单；元数据/源码仅生成结构型断言，杜绝"自洽但错误"的假期望。
- **呈现层补齐**：UI 自动化以真实浏览器驱动 Odoo 前端，覆盖 RPC 黑盒无法触达的页面渲染 / 中文化 / 字段标签 / 页签惰性渲染 / 拦截弹窗；与 RPC 层同为黑盒，跑在主实例 8069（详见 `测试工程技术方案.md` §8）。
- **变更级防线（三支柱）**：现有测试是「功能级防线」（断言应然），行为围栏是「变更级防线」（差分实然）——不需要先知道历史需求是什么，就能保护全部现状（含从未归档的口头共识）不被无意破坏；差异必须有 intents（挂 REQ id）背书才放行，嫌疑不清零不许合入。围栏管安全、考古管理解、止血管未来，KB 是运行副产品而非前置工程。
