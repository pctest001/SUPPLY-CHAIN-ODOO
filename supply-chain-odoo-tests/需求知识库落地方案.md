> 本方案用「带来源与状态的活需求知识库」替代「单一 PRD 即真相」的假设。

## 一、目标与原则

### 目标
1. **真相分层**：不再假设任何单一文档完整，需求真相 = 多来源条目的并集 + 状态管理。
2. **缺口可见**：系统能主动报告「哪些行为没有需求依据」「哪些需求没有测试覆盖」。
3. **冲突可查**：新旧需求打架时不静默覆盖，标记 conflict 并保留双方来源。
4. **AI 生成有据**：所有 AI 生成（用例/判定）必须引用 REQ-xxx，引用可校验。

### 原则
- **增量落地**：每个 Phase 独立可用、独立验收，不推倒现有 L1–L6 体系，只做增强。
- **纯本地零依赖**：延续工程惯例——JSONL 存储、标准库优先，不引入向量数据库（Phase 0–4 用关键词/规则匹配即可，语义检索留作后续可选增强）。
- **人是最终裁决者**：系统只负责发现缺口/冲突并展示，状态变更（implied→active、标记 deprecated）由人确认。

## 二、数据模型（Phase 0 核心）

### Requirement 条目 schema

```json
{
  "id": "REQ-PO-007",
  "content": "采购订单金额超出预算上限时必须拦截，不允许提交",
  "module": "purchase",
  "source": "legacy:2024-变更单#882",
  "source_loc": "第3节·审批规则",
  "provenance": "legacy",
  "status": "active",
  "confidence": 0.9,
  "acceptance": ["超额提交返回 4xx 且订单状态不变", "拦截时给出明确错误信息"],
  "related": ["REQ-PO-001"],
  "created_at": "2026-07-24T23:00:00",
  "updated_at": "2026-07-24T23:00:00",
  "notes": ""
}
```

### 字段约束

| 字段 | 取值 | 说明 |
|---|---|---|
| `id` | `REQ-<模块>-<序号>` | 全局唯一，模块缩写：PO/SO/INV/WH/RPT… |
| `provenance` | `current-prd` / `legacy` / `code-inferred` / `bug-derived` / `oral` | 来源类型，**永不修改**（历史事实）；`oral` = 线下口头共识经当事人确认后录入 |
| `status` | `active` / `implied` / `deprecated` / `conflict` / `undefined` | 当前效力，可随人工裁决流转 |
| `confidence` | 0.0–1.0 | current-prd=1.0，legacy=0.9，oral=0.8（经确认），bug-derived=0.8，一句话薄条目=0.7，code-inferred=0.6 起 |
| `acceptance` | 字符串数组 | 可验证的验收断言，是生成测试用例的直接素材 |

### 状态流转规则

```
code-inferred 产出 → implied ──人工确认──→ active
                              ──人工否决──→ deprecated
新需求与旧 active 互斥 → 双方标 conflict ──人工裁决──→ 一方 active / 一方 deprecated
PRD 未覆盖且无任何来源 → undefined（占位，提醒补需求）
```

## 三、分阶段执行计划

### Phase 0：数据模型与本地存储（Task #75）

**产出文件**
```
kb/
├── __init__.py
├── model.py      # Requirement dataclass + Provenance/Status 枚举 + validate()
└── store.py      # JSONL 读写 + 按 status/provenance/module 过滤 + upsert(按 id)
data/
└── requirements.jsonl   # 知识库本体（纳入 git 追踪）
```

**关键设计**
- `store.py` 提供：`load_all()` / `save(req)` / `query(status=..., module=..., provenance=...)` / `next_id(module)`。
- upsert 时旧版本追加到 `data/requirements_history.jsonl`（审计轨迹，git 忽略）。
- `model.validate()` 校验 id 格式、枚举合法性、acceptance 非空（active 状态强制）。

**验收**：单元测试——写入 1 条、按状态过滤、upsert 后历史留痕。

### Phase 1：多源需求采集（Task #76）

**产出文件**：`kb/loaders.py`

**三个采集器**

| 采集器 | 输入 | 输出 provenance/status | 方法 |
|---|---|---|---|
| `load_current_prd(path)` | 当前 PRD markdown | current-prd / active | 按标题层级切分，每个含「必须/不允许/应当/需要」的段落成候选条目，`source_loc` 记录章节路径 |
| `load_legacy(path)` | 历史 PRD、变更单、会议纪要（txt/md） | legacy / active | 同上，source 前缀 `legacy:<文件名>` |
| `infer_from_tests()` | `tests/`、`eval/eval_set.json` | code-inferred / implied | 解析测试函数 docstring 与断言，反推「代码正在保证的规则」，生成 implied 候选待人工确认 |

**关键设计**
- 采集器只产出**候选**，写入前做去重（content 归一化后相似即跳过，规则：去空白/标点后前 40 字符相同）。
- 每次采集输出 `采集报告`：新增 N 条 / 跳过重复 M 条 / 待人工确认 K 条。

**非规范历史需求的条目化策略（一句话需求 + 线下口头共识）**

现实约束：大量历史需求是一句话描述，还有一部分是线下与测试/开发达成一致、从未归档进 PRD 的口头共识。对策分三条线：

1. **一句话需求 → 薄条目直接入库**：一句话就是 content，acceptance 留空，confidence=0.7。原则是「先占 ID，后补血肉」——有 ID 测试用例才能挂上去，acceptance 空缺会被 Phase 2 审计自动列入缺口清单，倒逼逐步补全。禁止用 AI 直接把一句话「脑补」成完整需求写入 active；AI 只能产出 implied 候选。
2. **口头共识 → 反推 + 批卷子**：口头共识若真正重要，几乎必然已落进代码和测试。所以主力是 `infer_from_tests` 反推出 implied 清单，然后**拿清单找当事人（测试/开发同学）批卷子**——逐条确认/否决/补充，每条秒级，远比开「回忆会」高效。确认后 provenance 记 `oral:<日期>-访谈@<人名>`，confidence=0.8。辅助来源：群聊记录、工单、bug 单（bug-derived）。
3. **增量截流（防止暗需求继续产生）**：从 KB 建立之日起立规矩——线下达成一致的需求点，当场 5 分钟内补一条 REQ（provenance=oral），谁拍板谁录入。**存量靠逆向重建，增量靠截流**，否则边清边欠永远清不完。

排期建议：不做全量条目化，按模块风险排序——近半年改动频繁或出过线上 bug 的模块先做。

**验收**：三类来源各产出 ≥1 条入库，且能从 `source_loc` 回溯到原文位置；薄条目与 oral 条目各落库 ≥1 条验证 schema 兼容。

### Phase 2：缺口与冲突检测（Task #77）

**产出文件**：`kb/audit.py`，输出 `kb/gap_report.json`、`kb/traceability.json`

**四个检测**

1. **孤儿行为**：测试用例/eval 条目没有对应 REQ → 生成 implied 候选（说明代码里藏着没写下来的需求）。
2. **孤儿需求**：active REQ 没有任何测试覆盖 → 缺口清单（说明需求写了但没人验证）。
3. **冲突检测**：同一 module 下规则互斥（规则法：同对象出现「必须 X」与「不允许 X」/数值阈值不一致）→ 双方标 conflict。
4. **追溯矩阵**：`traceability.json` 记录 REQ ↔ 测试用例（文件::函数名）↔ eval 条目 id 三向映射。

**匹配方法**（零依赖版）
- 测试用例 ↔ REQ 关联优先用**显式标注**：测试 docstring 里写 `[REQ-PO-007]`；无标注时用关键词交集打分（阈值可调），低置信匹配进「待人工确认」列表而非直接写入。

**四源交叉验证（自动定信机制）**

以「代码反推的行为副本」为基准，与另外三个来源做匹配：①历史 PRD、②测试方案/测试用例、③技术方案。每条候选需求得到一个 4 位证据签名 `[代码, 测试, PRD, 技术方案]`，据此自动定信——**匹配不上不等于不可信，缺哪一源本身就是诊断结论**：

| 代码 | 测试 | PRD | 技术方案 | 自动诊断 | 处置 |
|---|---|---|---|---|---|
| ✓ | ✓ | ✓ | ✓ | 可信需求 | 自动 active，confidence=1.0，无需人工 |
| ✓ | ✓ | ✗ | ✗ | 暗需求（口头共识已落码） | implied，confidence=0.8，进访谈清单高优确认 |
| ✓ | ✗ | ✓ | ✓ | 无测试兜底 | active 但列入补用例缺口清单 |
| ✗ | ✗ | ✓ | ✓ | 未实现或被砍 | undefined，告警：文档与现实脱节 |
| ✗ | ✓ | — | — | 死测试/测试对象已删 | 测试侧告警，清理候选 |
| ✓ | ✗ | ✗ | ✗ | 仅代码单源 | code-inferred/implied，confidence=0.6，待验证 |

- 对齐方法（最难的部分）：不做全文相似度，用**强锚点**对齐——模块名 + 实体/字段名 + 数值（金额、天数、阈值）+ 状态名。数值和实体名区分度最高；锚点命中 ≥2 才算匹配，1 个进待确认。
- 3/4 及以上匹配即可自动转 active（阈值可配置），用证据冗余替代人工确认；证据签名与各源出处存入 `evidence` 字段随条目落库。
- 产出物：`kb/evidence_matrix.json`（每条需求的四源签名 + 出处）。

**岁月验证（stability，第五维证据）**

长期运行未变更且持续被调用的代码，等价于每天通过一次隐式全量回归——本身就是强证据，可用于弥补文档/测试/技术方案单源缺失。

- 稳定度自动计算（零人工）：`stability = f(无变更天数, 历史 bugfix 次数, 调用热度)`。无变更天数与 bugfix 次数来自 `git log --follow`；调用热度来自生产日志或覆盖率数据。
- **四象限规则**（防「死代码陷阱」——没变更可能是因为没人用/没人敢动）：
  - 老而热（无变更 ≥1 年 且 调用热度高）：岁月验证成立，confidence=0.9，即使孤源也可自动 active，备注 `time-tested`；
  - 老而冷：疑似死代码/僵尸规则，**禁止回填文档**，进清理评估清单；
  - 新而热/新而冷：按普通 code-inferred（0.6）走常规流程。
- 低频分支降信：即使在 time-tested 代码内部，从未被生产触发过的边界分支不继承 0.9（长寿 bug 多藏于此）。

**反向文档回填（用 time-tested 代码补齐缺失文档）**

对「老而热」条目执行三类回填，产物均标注「由代码反推 · 岁月验证」：
1. **PRD 补章**：从条目 content + acceptance 生成 PRD 补充章节（`docs/prd-backfill/`），意图描述由 LLM 起草、标 draft；
2. **特征锁定测试（characterization tests）**：不判断对错，把现有行为锁定为基准，防后续改动无意破坏——这是遗留系统标准手法，也是回填测试缺失的首选；
3. **技术方案补写**：从代码结构（模型/约束/状态机）生成实现说明骨架。

**验收**：对现有 56 条用例跑全量审计，产出 gap_report.json，人工抽查 3 条结论准确。

### Phase 3：与现有质量体系集成（Task #78）

**改动文件**：`eval/run_eval.py`、`eval/eval_set.json`、`prodmon/hallucination_judge.py`、`prodmon/badcase.py`

**三条集成线**

1. **eval 侧（生成有据）**
   - eval_set 条目增加 `req_id` 字段；新增 `kb/gen_eval.py`：从 active REQ 的 acceptance 自动生成 eval 候选条目（人工审核后合入 eval_set.json）。
2. **hallucination_judge 侧（引用校验）**
   - 判定时把相关 REQ（同 module 的 active 条目）注入上下文；
   - 硬约束：AI 输出必须引用 `REQ-xxx`；**引用不存在的 id、或引用 deprecated/conflict 条目 → 直接判幻觉**（这是根治「一本正经胡编」的关键闸门）。
3. **badcase 回流（闭环）**
   - `bad_cases.jsonl` 中的失败样本分类回写：因需求缺失导致 → 新增 bug-derived 条目；因需求打架导致 → 标 conflict。

**验收**：跑一轮 `run_eval` + `run_monitor`，报告中出现「req_id 引用率」指标（引用率 = 带合法 REQ 引用的输出 / 全部输出）。

### Phase 4：CI 集成、报告呈现与维护 SOP（Task #79）

**改动文件**：`reports/collect.py`、`reports/render_html.py`、`reports/render_markdown.py`、CI 配置、`质量体系架构.md` 等 4 文档

1. **报告卡片**：dashboard 与 Markdown 报告新增「需求知识库」卡片——需求总数、状态分布（active/implied/conflict/deprecated）、测试覆盖率（有测试的 active REQ 占比）、未决冲突数。
2. **CI 门禁**：新增 `kb-audit` 步骤跑 `kb/audit.py`；**冲突数 > 0 或覆盖率较基线下降 → 告警**（复用 notify.py），不阻塞合入（先观察一个迭代再决定是否升级为硬门禁）。
3. **维护 SOP**（写入本文档附录 + 质量体系架构.md）：
   - 新 PRD 到达 → `load_current_prd` 采集 → 跑 audit → 处理新冲突/缺口 → 确认 implied；
   - 需求变更 → 旧条目标 deprecated（不删除），新条目关联 `related`；
   - 线上发现遗漏 → badcase 回流自动建 bug-derived 条目 → 人工补 acceptance → 生成用例。

**验收**：CI 跑通一次、dashboard 出现 KB 卡片、4 文档同步完成。

## 五、风险与回退

| 风险 | 缓解 |
|---|---|
| 关键词匹配误关联 REQ 与用例 | 低置信匹配只进待确认列表；推显式 `[REQ-xxx]` 标注习惯 |
| 采集器把 PRD 切得过碎/过粗 | 候选先落 implied，人工确认后才 active；采集报告可回溯 |
| 引用硬约束导致 judge 误杀 | Phase 3 先以「引用率」为观察指标跑一个迭代，再启用直接判幻觉 |
| KB 无人维护而腐烂 | CI 每次跑 audit 暴露腐烂信号（覆盖率下降/冲突堆积），报告卡片常驻可见 |

**回退方案**：KB 全部是新增文件（`kb/`、`data/requirements.jsonl`），对现有模块的改动只有「注入上下文 + 加字段」，任一阶段不满意可直接停用（judge 不注入即退回原行为），零破坏。
