# supply-chain-odoo 自动化测试工程 · 技术方案

> 版本：v3.0（v2.3 基础上新增：行覆盖率度量体系、Mutation 门禁（反假绿）、AI 非降级链路、sc_log_trace 纳入，共 40 passed）
> 目标系统：`supply-chain-odoo`（Odoo 18，模块 `supply_chain_demo` + `sc_ai` + `sc_log_trace`，DB `supplychain`，端口 8069）
> 本工程为**独立仓库**，仅通过 RPC 驱动目标系统，不 `import odoo`、不挂载 `custom_addons`。

---

## 1. 设计原则

1. **只做黑盒驱动**：测试工程通过 XML-RPC / JSON-RPC 与被测 Odoo 交互，绝不 `import odoo` 包，绝不修改 SUT 业务代码。**被测 Odoo 实例本身须包含 `custom_addons`（含 `supply_chain_demo` + `sc_ai` + `sc_log_trace`），由测试 compose 拉起；测试工程代码不挂载 `custom_addons`，仅作为外部 RPC 客户端。**
2. **自愈三边界 + 审计**：自愈只作用于 **环境 / 数据 / 配置** 三层，绝不自动改业务代码；发现代码缺陷只报告人工（已实践：AI 临期批次工具字段 bug 由人工修复、独立 commit）。**自愈每次动作须记审计日志（什么坏了 / 修了什么 / 用的策略）；自愈救场后用例必须重跑，仍失败才判 SUT 缺陷；配置层"受控脚本"设触发门槛（如连续 N 次环境异常才自救），避免单次抖动误救，更避免把 SUT 真实回归"修绿"而掩盖问题。**
3. **确定性用例 + 期望值权威**：用例由已知期望驱动、写明确断言、判定 pass/fail。**业务期望以 PRD / 验收清单为唯一权威；元数据（`ir.model.fields` / `ir.rule`）与源码静态分析仅用于生成"结构型断言"（必填缺失应报错、跨公司应拦截、字段/方法存在），不用于推导"数值型业务断言"，避免从代码反推期望再断言代码导致自洽但错误。**
4. **反假绿双保险（v3 新增）**：
   - **行覆盖率量化**：证明"哪些代码被真正执行"，把盲区（未覆盖代码）显式呈现为补测地图；
   - **Mutation 门禁**：注入语义变异后，对应用例**必须变红**，否则判"测试过弱"——证明用例能抓住真实缺陷，而非巧合通绿。

## 3. 被测系统架构（P0#1 澄清）

这是方案能否跑通的前提，明确"测试工程"与"被测系统"的边界：

- **测试工程**：独立仓库，只持有 RPC 客户端与生成/自愈逻辑，**不挂载 `custom_addons`**，不 `import odoo`。
- **被测实例**：由 `docker-compose.test.yml` 拉起一份**含 `custom_addons` 的 Odoo**（把 `../custom_addons` 挂载到**被测容器** `/mnt/extra-addons`）。要测 `sc.purchase.request`、`sc.log.trace` 等模型，被测实例必须有这些模块——**当前受控安装 `supply_chain_demo, sc_ai, sc_log_trace` 三个模块**（v3 新增 `sc_log_trace`）。
- **通信方式**：测试工程通过 `18069`（测试实例独立端口，避免与主项目 `8069` 冲突）连被测实例，进程隔离、无代码共享。
- **为什么不混在一起**：测试工程可独立部署、独立 CI；被测实例则等价于"生产镜像 + 我们的模块"，保证测的是真实业务代码。

```
[ supply-chain-odoo-tests ]  --XML-RPC/JSON-RPC:18069-->  [ 被测 Odoo（含 custom_addons） + postgres ]
   仅 RPC 客户端                                 被测系统（测试 compose 拉起，挂载 ../custom_addons）
```

### 3.1 覆盖率注入（v3 新增，解决"黑盒测容器内代码"）
被测容器本身不预装 coverage、也不主动测量。通过在 `docker-compose.test.yml` 注入：
- `COVERAGE_PROCESS_START=/mnt/covdata/.coveragerc`：每个 Python 进程（含 Odoo 启动时的 re-exec 子进程）经 sitecustomize 自动 `coverage.process_startup()`；
- `PYTHONPATH=/mnt/covdata/sitecustomize`：挂入自写的 `sitecustomize.py`（开启 parallel 模式、指定数据文件 `/mnt/covdata/.coverage`）；
- `./covdata:/mnt/covdata`：覆盖率数据卷，宿主机可读合并；
- `--db-filter=^test_supplychain$`：避免误测其它库。
采集为多进程 parallel：odoo 主进程 + 子进程各自写 `.coverage.<host>.<pid>`，停 odoo（SIGTERM 触发 `atexit` 落盘）后由宿主机/容器内 `coverage combine` 合并，再由容器内 `coverage report/html` 出报告（容器内路径匹配更稳）。

## 4. 方案主体（v1 / v2 / v3）

### 4.1 脚本化用例生成（三类来源 + 期望值权威，P0#3）

- **① Odoo 运行时元数据** → 结构型断言：`required=True` 字段缺失 `create` 应报错；`ir.rule.domain_force` 含 `company_id` → 跨公司 uid 搜不到该记录；字段/方法存在性。
- **② 源码静态分析** → 结构型断言：`Selection` + `action_*` 生成状态机用例；`raise UserError` / `ValidationError` / `@api.constrains` / `_check_*` 生成异常路径"应被拦截"断言。
- **③ PRD / 技术方案** → 业务型断言（权威）：`验收清单.md`、`作品说明.md`、`演示走查脚本.md`、EARS 注释中的数值/流程期望，作为 pass/fail 的唯一权威来源。

> **红线**：②③类（元数据/源码）只生成"结构型断言"（是否报错、是否拦截、是否存在）；业务数值期望只来自 ③ PRD。禁止用代码反推数值再断言代码，否则是"测了个假期望"。

### 4.2 自愈三层 + 审计与不掩盖回归（P0#2）

- **环境层**：容器未起 / 端口不通 → 探活重试、必要时拉起 `docker-compose.test.yml`。
- **数据层**：依赖演示数据缺失 → `data_repair` 用 RPC 重建（不碰业务代码）。
- **配置层**：模块未装 / 参数错误 → `diagnostics` 校验并给修复建议；"受控脚本"执行，且设**触发门槛**（如连续 N 次异常才自救），避免单次抖动误救。
- **审计（关键）**：所有自愈动作写入 `audit.py` 日志（异常现象 / 修复动作 / 使用策略 / 时间戳）。
- **不掩盖回归**：自愈救场后，原用例**必须重跑**；重跑仍失败 = SUT 真实缺陷（报警）；重跑通过 = 确为环境/数据/配置问题。**绝不因自愈成功就直接判定用例通过。**

### 4.3 需求-用例双向追溯

给每条 PRD / 验收项分配稳定 ID（如 `C3-01`，绑定需求条目而非行号），生成用例时把该 ID 写入用例元数据；测试报告可反查每条需求被哪些用例覆盖，支持覆盖度统计。

### 4.4 行覆盖率度量（v3 新增：量化"测到了多少"）

黑盒 RPC 无法直接 `import` 被测代码，故用 **sitecustomize + `COVERAGE_PROCESS_START` 子进程注入**(§3.1) 实现"在容器内、测黑盒驱动到的真实代码行"。

**运行（一键）**：
```powershell
cd supply-chain-odoo-tests
powershell -ExecutionPolicy Bypass -File run_coverage.ps1
```
脚本 7 步：起容器 → 确保容器内装 coverage（幂等自修复）→ 清旧数据 → 重启 odoo 进入测量态 → **跑全部用例**（pytest 结果打印）→ 停 odoo 落盘并 `combine` → 容器内 `coverage report`（终端表格 + `cov_report.txt` + `covdata/htmlcov/index.html` 逐行标红）。

### 4.5 Mutation 门禁（v3 新增：反假绿 A2 自动化）

覆盖率高≠用例有效。门禁逻辑收敛在 `mutation_gate.py`（本地/CI 双用，跨平台），对每个变异点执行：**精确注入 → `restart odoo` 重载 → 只跑对应用例（期望变红）→ `finally` 还原源码**；任一变异未被抓住（用例仍绿）⇒ 测试过弱 ⇒ 退出码非 0 ⇒ CI 失败。字节级替换保留原文件换行符，避免 CRLF 污染。

| ID | 变异内容 | 应抓住它的用例 | 来源 |
|----|---------|---------------|------|
| M1-PR-SUBMIT | `action_submit` 提交后不置 `confirmed`（状态机断裂） | `PR-SUBMIT` | purchase_request.py |
| M2-RCPT-NOLOT | C3 收货批次守卫被绕过（无批次也放行） | `test_rcpt_nolot_rejected` | stock_receipt_lot.py |
| M3-RECIPE-QTY | 配方用量约束 `<=0` 松成 `<0`（零用量放行） | `C-RECIPE-QTY` | recipe.py |
| M4-ACK-CONFIRM | `action_confirm` 确认后不置 `confirmed`（状态机断裂） | `ACK-CONFIRM` | supplier_ack.py |
| M5-PO-CONFIRM-GUARD | `button_confirm` 审批守卫被删除（未审批也能确认订单） | `PO-CONFIRM-GUARD` | purchase_order_approval.py |
| M6-PR-GENPO-NOPARTNER | `action_generate_po` 的『无供应商』守卫被删除（无供应商也能生成 PO） | `PR-GENPO-NOPARTNER` | purchase_request.py |

**本地验证**：`python mutation_gate.py` → `caught=['M1-PR-SUBMIT','M2-RCPT-NOLOT','M3-RECIPE-QTY','M4-ACK-CONFIRM','M5-PO-CONFIRM-GUARD','M6-PR-GENPO-NOPARTNER'] missed=[]`（6/6 全部被抓住 ⇒ PASS）。CI 中同一脚本跑在 `if: always()` 之外、失败即阻断合并。

### 4.6 AI 智能层测试（v3 新增：降级 / 非降级两条线）

AI 能力（对话、预警解读、补货建议、6 个白名单工具）须分两条链路测，否则只测降级会留下 §4.4 中 `ai_models` 仅 48.8% 的盲区、藏匿真实 bug。

- **降级链路**（`test_ai.py`，marker `ai`）：无 LLM Key 时 `ai.chat.session.ask()` 返回非空降级文本、**绝不抛异常**（G5 全链路降级）。Key 缺失由被测实例 `SUPPLY_AI_API_KEY` 环境变量控制。
- **非降级链路**（`test_ai_llm_mock.py`，marker `ai`）：宿主机起 OpenAI 兼容 **mock server**，容器经 `host.docker.internal` 回连（不可达则整组 skip，不误红）。跑通 Function Calling 两轮对话：6 个白名单工具全触发 + 白名单外注入拒绝 + 坏参数兜底 + 侧边面板 `chat()` API + 会话生命周期 + 预警/补货走 LLM 路径。
- **Key 红线不破**：测试只设 `api_key_env` 指向容器内必存在的 `PATH` 环境变量名，Key 内容对 mock 无意义——**绝不把真实 LLM Key 写进仓库**。
- **实践收益**：补这 6 条用例首次真正驱动 `query_expiring_lots` 工具，暴露并修复了 `ai_models._tool_query_expiring_lots` 误用 `stock.lot.quantity`（Odoo 18 应为 `product_qty`）的真实 bug（独立 commit `be64fa9`）。

### 4.7 L4 AI 评测层（v3.1 新增：测 AI 本身 + 度量度量者）

§4.6 只验证了 AI 的"功能/安全"（降级、非降级、注入拒绝）。但"AI 辅助测试"主线还要求**量化 AI 回答本身的质量**——幻觉率、准确率、拒答率、安全违规率，并在每次变更做回归基线。这部分落在 `eval/` 包，纯标准库、离线可跑。

- **金标准 `eval_set.json`**：14 条人工标定用例，覆盖 6 个白名单只读工具（`query_stock`/`query_purchase_orders`/`query_suppliers`/`query_expiring_lots`/`query_low_stock`/`query_supplier_acks`）+ 3 类拒答（提示词注入 / 坏参数兜底 / 超范围）。每条含 `expected_tools`、`refuse`、`must_not_contain`（幻觉标记）、`gold_keywords`。
- **裁判 `judge.py`**：
  - `RuleJudge`：确定性比对 trace（实际调用的工具 / 是否拒答 / 回答文本）与金标准，输出 `accurate / hallucinated / refused_correctly / safe`；
  - `LLMJudge`：可插拔接口，内置 `MockLLMJudge`（离线，与 RuleJudge 结论一致）+ `RemoteLLMJudge` 桩（读 `SUPPLY_EVAL_JUDGE_URL` 环境变量，未配置即 `NotImplementedError`，**绝不伪造远程评分**）。
  - `compute_metrics()`：准确率 / 幻觉率 / 拒答准确率 / 安全违规率 / `quality_score = 100·accuracy·(1-幻觉率)·(1-安全违规率)`。
- **引擎 `engine.py`**：
  - `MockAIEngine`（sim，离线）：忠实重放 sc_ai 设计契约（工具路由 / 注入拒答 / 坏参兜底 / 超范围拒答），无需 Odoo，用于验证"裁判+指标+基线"链路；
  - `LiveAIClient`（live）：经 `odoo_client` 驱动真实 SUT，读 `ai.chat.session` 消息还原 trace。注：当前 sc_ai 不落 tool_call 日志，live 模式对"工具准确率"暂需后续在 `ai_models` 增加 tool_call 记录才能精测。
- **运行器 `run_eval.py`**：`python -m eval.run_eval --mode sim --fail-under 80` → 写 `eval_report.json` + `eval_baseline.json`，与基线对比检测回归；`quality_score` 低于阈值即 `exit 1`（CI 门禁）。`--judge remote` 可接真实 LLM-as-Judge。
- **有效性度量 `effectiveness.py`（§8 度量度量者）**：读 `mutation_out.json` 算**北极星逃逸率 / 拦截率 / 误报率**；复用 `eval_baseline.json` 的 AI 指标；`calibrate()` 计算 RuleJudge/LLMJudge 与人工金标准的 **Cohen's kappa** 校准（防"评测分高但线上翻车"）；`quasi_experiment_notes()` 给出上线前后生产逃逸率差分方法（待生产埋点）。当前实测：逃逸率 0%（Mutation 6/6 全抓）、拦截率 100%、`quality_score` 100、幻觉率 0、kappa 1.0。

> 与 §4.6 的边界：§4.6 是"AI 模块的功能/安全测试"（有没有按契约工作），§4.7 是"AI 输出的质量评测"（回答对不对、有没有幻觉、该拒的是否拒了）。两者互补，共同把 L4 闭环。

### 6.2 PRD 来源生成与 M2 增强（任务2）

### 6.2.1 M2 增强：守卫覆盖扩展
`metagen` 新增三类用例，覆盖更多业务守卫（由 `healer` 幂等造流程成品/原料/供应商/采购单供复用）：
- `CreateViolationCase`（constrains 在 create 路径触发）：配方用量必须大于0、原料不能与成品为同一物料。
- `WriteViolationCase`（constrains 在 write 路径触发）：配方至少需一种原料——注意 Odoo constrains 对 create 时未提供的字段不校验，故改用「先建合法配方再清空明细」触发。
- `CreateThenActionCase`（先建记录再调 action）：供应商交期确认单 `action_confirm` 缺交期应被拒。

### 6.2.2 PRD 来源生成（业务数值断言）
新增 `src/generator/prd_rules.py` + `prdgen.py` + `BusinessCase`：
- `prd_rules.py` 是**业务数值期望的唯一权威**，提炼自验收清单.md / 作品说明.md（C1 PR→PO、E 供应商交期确认单状态机），严禁从代码反推 state 字符串（P0#3 红线）。
- `prdgen` 把规则翻译为 `BusinessCase`（正向业务断言：执行 action，断言达到 PRD 规定的 state/字段）。
- 业务用例：PR-SUBMIT（提交后 confirmed）、PR-GENPO（生成PO后 done 且联动 po_ids）、ACK-CONFIRM（确认交期后 confirmed）。

### 6.2.3 实现中的关键经验（已固化到代码）
1. **action 返回值 None 致 XML-RPC 序列化失败**：Odoo 部分 action（action_submit/action_confirm）无返回值，XML-RPC 默认 `allow_none=False` 报 `cannot marshal None`。方法副作用（write 状态）已提交，故 `BusinessCase._call_action` 吞掉该类 Fault，以被测记录**实际 state** 判定，不依赖返回值。
2. **action 方法参数须以方法参数传入**：`action_confirm(self, committed_date=None, ...)` 的 `committed_date` 是方法参数而非记录字段，调用须 `execute(model, method, [ids], **{"committed_date": ...})`。
3. **调用约定**：`execute(model, method, [ids])` 正确（Odoo 端 browse(ids) 后调用）；把 kwargs 当位置参数传入会误变成多参而失败（`_call_action` 已用 `**` 展开修复）。
4. **PR 真实状态机**（PRD 权威，非代码反推）：提交态取值 `confirmed`、生成PO后取值 `done`（非 submitted/po_generated）。
5. **多公司环境锚定**：黑盒用例一律锚定 admin 当前公司，仓库/库位/作业类型按 `company_id` 过滤，避免跨公司混用导致误红。

### 6.3 CI 集成（双门禁，v3 升级）

`supply-chain-odoo-tests/.github/workflows/ci.yml` 提供 GitHub Actions 流水线，串起完整链路：
1. `docker compose up -d` 起被测 Odoo + Postgres（端口 18069/5433，挂载 `../custom_addons`）；
2. 等 Odoo HTTP 就绪；
3. 容器内装 coverage（持久卷，全新卷须先装，否则 sitecustomize 缺包静默不测量）；
4. `docker compose run --rm odoo odoo -i supply_chain_demo,sc_ai,sc_log_trace -d test_supplychain --stop-after-init` 初始化测试库并装三个业务模块；
5. restart Odoo 加载模块；
6. `pip install pytest` 后 `python -m pytest -v --junitxml=report.xml`；
7. **覆盖率门禁**：`stop odoo`（SIGTERM 落盘）→ 容器内 `coverage combine` → `coverage report --fail-under=70`（实测 85.1%，留 ~15pt 余量防抖动）→ 报告传 artifact；低于阈值则 CI 失败；
8. **Mutation 门禁**：`python mutation_gate.py`，6 变异点（M1–M6）任一未被抓住则 CI 失败，输出 `mutation_out.json` 传 artifact；
9. 始终上传 `report.xml`（JUnit）、`healer_audit.jsonl`（自愈审计）、`coverage_report.txt`、`mutation_out.json` 为 artifacts；
10. **AI 评测门禁**（独立 job `ai-eval`，离线无需 Odoo）：`python -m eval.run_eval --mode sim --fail-under 80` → `pytest tests/test_eval.py` → `python -m eval.effectiveness`，上传 `eval/eval_report.json`、`eval/effectiveness_report.json`。`quality_score` 不达标或逃逸率上升即 CI 失败。

触发：push/PR 到 main。确定性用例（M1+M2 结构型+业务数值+AI+多公司+收货+产品扩展+日志追踪）作为 blocking CI 稳定运行；**覆盖率门禁 + Mutation 门禁 + AI 评测门禁**构成三保险：前者量化"测了多少"，次者证明"测的是真的"，后者量化"AI 答得对不对（幻觉/拒答/安全）"；自愈三层在用例前准备环境并留痕，绝不捕获用例断言失败去自愈，因此不会掩盖真实回归。

## 8. UI 自动化（Playwright 黑盒浏览器，v3.x 新增）

> 补齐 RPC 黑盒测试的**呈现层盲区**：页面渲染 / 中文化 / 菜单导航 / 字段标签 / 自动保存 / 页签惰性渲染 / 拦截弹窗——这些 RPC 无法触达，却正是小白手工走查（演示走查脚本.md TC-B01~B09）关注的点。

### 8.1 定位与边界
- 同样遵守第 1 节「只做黑盒驱动」：**不 `import odoo`、不挂载 `custom_addons`、不修改 SUT 业务代码**。区别在于驱动方式：RPC 用例经 XML-RPC/JSON-RPC 调模型方法（验证守卫/状态机/数值），UI 用例经**真实浏览器（Playwright + Chromium）**连 Odoo 前端（验证呈现层）。
- **被测实例**：UI 用例跑在**当前主实例 `http://localhost:8069`**（即 `docker-compose.yml` 拉起、挂载 `../custom_addons` 的实例，与手工走查脚本同一实例），而非 RPC 测试的隔离实例（18069）。原因：UI 走查须驱动真实视图/菜单/中文化，依赖 `custom_addons` 的视图定义，且与手工走查同一实例才一致；RPC 隔离实例则用于可重装、可注入覆盖率的纯逻辑测试。两者互不干扰，但**不要在同一实例上并发跑 RPC 初始化与 UI 用例**。
- **环境约束**：宿主机代理白名单只放行少数域名（如 douban.com），装不了浏览器内核；Odoo 容器可直连外网。故 **Playwright + Chromium 装在容器内**，用例以黑盒客户端身份连 `localhost:8069`。

## 7. 关键结论

- 测试工程为独立仓库、仅 RPC 驱动；**被测实例须含 `custom_addons`（含 `sc_log_trace`）**，由测试 compose 拉起——这是跑通前提。
- 本期交付**确定性用例生成 + 三层自愈 + 行覆盖率度量 + Mutation 反假绿门禁**；自愈只救环境/数据/配置，且**全程审计、救场后重跑、不掩盖回归**。
- **业务期望以 PRD 为权威，元数据/源码仅生成结构型断言**，避免自洽但错误的假期望。
- **覆盖率量化盲区、Mutation 抓真 bug**：本轮靠覆盖率地图（`ai_models` 48.8% 盲区）驱动补测，第一次走通 AI 非降级链路即抓出 `product_qty` 真实 bug——印证"未覆盖处即 bug 藏身处"。
- 探索性测试暂缓，待基础稳固后再议。
